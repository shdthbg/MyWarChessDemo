> **标签**：`MoveRangeMeshUI` `NavMeshPathHelper` `NavMesh.CalculatePath`
> **成果**：持续 13ms/帧 → 单次 9ms（每秒累计开销 ↓98%）

---

## 一、问题表现

1. 玩家**静止且被选中**时，脚本开销持续高企（约 13ms/帧）
2. 玩家**开始移动**，开销迅速回落至正常
3. 纯探索阶段即可复现，与入战无关

**关键线索**：「移动时反而正常」这个反直觉现象，直接指向「仅静止时执行」的代码。

## 三、根因

**问题 1：错误的「每帧重算」模型**
`ShowRange()` 是**状态变更操作**，却被放在 `Update()` 里每帧执行。范围圈只在「选中瞬间 / 停止移动瞬间」需要重算。

**问题 2：算法三重低效**
- 外圈点注定不可达，却仍打射线、算寻路
- 每次 `new NavMeshPath()`
- `Dictionary` 哈希 + 排序闭包 + `Take(64)`

## 四、修复

### 1. 状态标志替代每帧调用 ⭐ 核心

```csharp
private bool _rangeShown = false;

private void Update()
{
    if (SelectEvent.Instance == null || navMeshMoveCtrl == null) return;

    bool isSelected = gameObject == SelectEvent.Instance.CurrentSelectedCharacter;
    bool shouldShow = isSelected && !navMeshMoveCtrl.isMoving;

    if (shouldShow && !_rangeShown)              // 隐藏→显示：算一次
    {
        ShowRange();
        _lastRangeCenter = center;
        _rangeShown = true;
    }
    else if (shouldShow && _rangeShown
             && Vector3.Distance(playerAgent.transform.position, _lastRangeCenter) > recomputeThreshold)
    {
        ShowRange();                             // 移动超阈值：重算
        _lastRangeCenter = center;
    }
    else if (!shouldShow && _rangeShown)         // 显示→隐藏：关闭
    {
        HideRange();
        _rangeShown = false;
    }
}
```

**仅此一项：13ms/帧 → 9ms/次。**

### 2. 距离预筛提前

三角形不等式：**路径长度 ≥ 直线距离**。直线距离已超限的点，无需寻路。

```csharp
private void PruneOutOfRange(List<Vector3> points)
{
    float maxSqr = maxMoveDistance * maxMoveDistance;
    int write = 0;
    for (int i = 0; i < points.Count; i++)
    {
        float dx = points[i].x - center.x;
        float dz = points[i].z - center.z;
        if (dx * dx + dz * dz <= maxSqr)
            points[write++] = points[i];   // 原地压缩，零分配
    }
    if (write < points.Count)
        points.RemoveRange(write, points.Count - write);
}
```

裁剪提前到射线之前，射线数同步下降；半径余量 `+1f` → `+0.5f`，点数再降约 31%。

### 3. NavMeshPath 复用

```csharp
// NavMeshPathHelper 新增重载
public static float GetPathLength(Vector3 start, Vector3 end, NavMeshPath reusablePath)
{
    if (reusablePath == null ||
        !NavMesh.CalculatePath(start, end, NavMesh.AllAreas, reusablePath))
        return Mathf.Infinity;

    if (reusablePath.status != NavMeshPathStatus.PathComplete)
        return Mathf.Infinity;

    float length = 0f;
    for (int i = 1; i < reusablePath.corners.Length; i++)
        length += Vector3.Distance(reusablePath.corners[i - 1], reusablePath.corners[i]);

    return length;
}
```

**分配量：1200 个/轮 → 1 个/轮。**

## 五、坑点记录

### 坑 1：NavMeshPath 不能在字段初始化器中创建

```csharp
// ❌ UnityException: InitializeNavMeshPath is not allowed
//    to be called from a MonoBehaviour constructor
private readonly NavMeshPath _cachedPath = new NavMeshPath();

// ✅ 字段只声明，Awake 中创建（readonly 也需去掉）
private NavMeshPath _cachedPath;
void Awake() { _cachedPath = new NavMeshPath(); }
```

Unity 原生对象（`NavMeshPath`、`Texture2D`、`Mesh`、`Material`）都应在 `Awake()`/`Start()` 中创建。

### 坑 2：重构误删 `center` 赋值 → 范围圈消失

原 `Update()` 中的 `center = transform.position;` 被连带删除，导致 `center` 恒为 `Vector3.zero` → 采样点在原点 → 射线打不到地形 → 无可达点 → 不绘制。

**修复**：把赋值移入 `ShowRange()`（唯一使用方），避免再被误删。

**教训**：对「看似无关的一行赋值」要警惕——可能被下游方法隐式依赖。

## 六、优化效果

| 指标 | 优化前 | 优化后 | 降幅 |
|---|---|---|---|
| 脚本耗时 | 13ms **每帧** | 9ms **单次** | — |
| 每秒累计 | ~780ms | ~9ms | **↓ 98.8%** |
| NavMeshPath 分配 | ~1200 个/轮 | **1 个/轮** | ↓ 99.9% |
| List 分配 | 4~5 个/轮 | **0** | ↓ 100% |
| 外圈提取 | O(n log n) + 哈希 | O(n) 数组 | — |
| 圆环缺口 | 存在 | 已修复 | — |

**剩余单帧峰值评估**：9ms 属可接受范围——频率从每秒 60 次降为每次交互 1 次；发生在操作间隙；回合制无实时压力；Editor 下通常被放大 3~5 倍，打包后约 2~4ms。

如仍需压缩：`sampleDensity` 调参 → 协程分帧构建 → 只沿边界步进采样。

## 七、方法论总结

1. **反直觉现象是最好的线索** — 「移动时正常、静止时高开销」直接框定了嫌疑范围
2. **区分「状态变更」与「持续更新」** — 面板显隐、范围重绘属变更逻辑，不应放进 `Update()` 每帧跑
3. **先算清量级再动手** — 1200 点 × 2 次昂贵调用 × 60fps = 每秒 14.4 万次，优化效果同样用数字验收
4. **复用 > 优化** — 消除 72,000 对象/秒的 GC，收益远超算法微调；先消除分配，再优化算法
5. **优化会顺手挖出 Bug** — 均匀抽稀的修正是优化过程中发现的
